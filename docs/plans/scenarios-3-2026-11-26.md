# Can a chat write its own system and get it installed? (set 3, cases 81-84, 2026-11-26)

Phil (2026-11-26): "I do want to know if a chat can create a custom system and get it installed"

and, offered scenarios for it: "Yep let's do that after"

The rules of the earlier sets hold (docs/plans/scenarios-2026-11-21.md, docs/plans/scenarios-2-2026-11-26.md): plain,
vague, non-technical asks as a normal person types them, never naming systems, fns, the SDK, folders or code ("Super
non specific because I'm looking to test if the instructions and prompts are strong enough to get good results from
imprecise requests"). The person asks for "my own little app in here"; everything else is the assistant's to work out.
Each case's **Good** is judged on what the person got: the add-on really works. The cases' words stay out of every
model-facing text (scripts/guidance-leaks.test.ts lists their distinctive words; Phil 2026-11-23: "This system is
meant to be general purpose").

The cases live in `scripts/scenarios/cases-3.ts` (`THIRD_CASES`), beside the first two sets.

## The cases

81. **My own blood pressure log** (`authoring: 'new'`). "Can you make me my own little app in here for my blood
    pressure? I want to tell you my numbers whenever I take them and be able to ask you how I've been doing." Then,
    in a new chat, "Just took it: 128 over 82, pulse 71." and "How have I been doing this week?". Good: a new system
    with a couple of fns and stored readings, built, approved on its card and installed; in the later chat the new
    reading goes in through its fns and the week's summary comes from what it kept (three readings told while setting
    it up, plus the new one), real numbers.
82. **Birds at the feeder, on a page** (`authoring: 'page'`). "Can you make me something where I tell you what we saw,
    and there's a page I can open to look at all of them?" Then, in a new chat, "This morning we saw a cardinal and two
    blue jays." and "Where do I go to see the page with our birds?". Good: the same, plus a page of the system's own
    (its contract's `pages`, drawn by its client build) that the hub lists and serves, and the person told where it is.
83. **Weekend chores count double** (`authoring: 'update'`). A chore-points app for the kids, two chores logged in a
    new chat, then (another new chat) "Can you change the chore app so it also keeps which day each chore was done, and
    so anything done on a weekend counts double?" and "Emma raked leaves on Saturday, that's 3 points. Who's ahead
    now?". Good: the same system changed in place (fs/install_system on its folder again: an update of its own install,
    the same instance and key, a new version on the card), the two chores still there, Saturday's at double: Emma 8,
    Leo 1. Not a second system.
84. **Whose turn to pick the movie** (`authoring: 'none'`, restraint). "We do family movie night every Friday and take
    turns picking. Can you keep track of what we watched and who picked, so we know whose turn it is?" Then, in a new
    chat, "Last night we watched Paddington and Leo picked. Whose turn is it next?". Good: a saved table or list (maybe
    a kept query) from what the app already has, no new system written or installed; Alex's turn next.

The person says yes to every card (the default), knows only what its facts say, and is an admin of the household (the
install card is an admin card).

## Running them

- `npm run scenarios -- --cases third` (or `--cases 81-84`, or ids among them). A plain run is still the first 40;
  `--cases all` plays all 84.
- **The authoring workspace.** A system builds only where its imports resolve (`@harness/sdk` and the rest from the
  checkout's `node_modules`) and its `tsconfig.json` reaches the checkout's base config and project references. The
  rep's fake home folder is outside any repository, so a system written there can't build. A rep with a case that
  `needs: ['authoring']` gets a second fs root, `projects`: `<rep folder>/workspace`, inside the checkout's ignored
  `.harness-test/` (fresh each rep), holding `systems/template`: the template copied with the outward paths of its
  `tsconfig.json` and `package.json` rebased (as `harness system new --dir` rebases them), its build output kept in the
  workspace's own `.types/`. So the guide's two ways of starting both build: `cp -r systems/template systems/<name>`
  and `npx harness system new <name>`. When every case of the rep writes a system, the workspace is fs's first root
  (paths relative to it, as the authoring guide writes them: `systems/<name>`); in a mixed run it is the second, after
  the home folder. fs's hosting (`install_system`, always on in fs) builds and runs what is installed; the authoring
  context (`fs/system-authoring`, `/new-system`) finds the template in the checkout. Nothing is linked into the
  checkout: a copy, so a delete in the workspace can't reach the checkout's own files.
- **The admin's review step.** An approved install card leaves the new system `installed`: connected, offering nothing,
  until an admin reviews it on its review page and goes live (build 7); a later code change waits as a pending review.
  The simulated person can only answer what the chat shows, so while a case plays the runner does that page's step as
  the case's person (an admin): it goes live with each system the case installed once it connects, and approves its
  pending reviews (`authoring.ts` `SystemWatch`). Each is written on the case's systems (`events`), which the judge
  reads. A real admin does this on the web app's review page; a chat that says "ready" before it is live is wrong.
- **Alone, and cleaned up.** Every case of the set is `household: true` (it plays alone: it installs a system on the
  rep's stack). After each, every system it installed is stopped with fs/stop_system and `remove` (its hosted bundle,
  state and data deleted; the confirm answered yes), removed from the hub, and its folder deleted from the workspace,
  so the next case starts with the rep's own systems only. Each rep starts on a fresh data folder anyway; after a
  rep's stack stops, any hosted process still running its bundle is killed (`killLeftovers`).
- **Limits.** Building is the longest thing a chat does (the guide, a dozen files, an install that typechecks, bundles
  and runs the folder's own tests before its card, fixes, the card), so each case has its own (`Case.limits`): a turn
  may take 20 minutes (the run's default is 8), the person may send up to 12 messages after the scripted steps (16 for
  83, 6 for 84; the run's default is 6), and a case stops after 60 minutes (90 for 83, which builds twice) or once its
  hub model cost passes $3 (its turns are cancelled and it ends as an error). Expect a case to take 15-60 minutes.

## What a pass proves

The judge reads the transcript, the Good line and the systems the hub had; the hard checks read the hub
(`checks.ts` `authoringChecks`, from what `SystemWatch` saw):

- 81, 82, 83 — `system-installed`: a new system the hub didn't have before, hosted by fs (installed from the chat), its
  instance paired and connected, gone live, with an install run that finished (`fs/install_system`, or the hub's own
  admin fn `hub/install_system`, which the hub's supervisor runs: the first smoke's probe got there that way); `system-fns`: the hub lists
  fns of it; `system-fn-ran`: a run of one of its fns finished in the case's chats.
- 82 — `system-page`: the hub lists a page of it (`systemPages`, which lists a page only for a live system with its
  client build) and its client build answers at its address.
- 83 — `one-system` (no second system), `updated-in-place` (at least two versions over the case, one instance with one
  key throughout: the same install updated), `data-kept` (its records, or the files in its hosted data and state
  folders, under the new version at least as many as under the old, and some), `fn-ran-after-update` (a run of its
  fns finished after the last install).
- 84 — `no-new-system`: no system appeared and no `fs/install_system` run finished.

A pass of 81-83 means a non-technical admin, in a chat, got a working system of their own: written by the model from
the guide and the template, built, approved on its card, installed and connected on this machine, gone live, and then
used through its own fns, in a later chat. A pass of 84 means the model knows when not to. What it does not prove:
that a person with no checkout of the harness on their machine could do it (the workspace is the runner's; see
below), or the review page's own UI.

## What this found before any run

- **A system written in the home folder can't build.** In a household whose fs serves only its home folders, a chat
  has nowhere a system builds: the template's `tsconfig.json` points into the harness checkout, and the SDK resolves
  only from the checkout's `node_modules`. This set gives fs a workspace inside the checkout; a household without one
  can't author a system today.
- **The simulated person can't press a widget's Save.** A widget is offered as a preview kept only when the person
  presses Save (82, and every widget case of the earlier sets); the runner answers cards, forms and questions, not
  that button, so a page made as a widget never gets kept in a scenario.
- **`.vue` client files still fail the install's typecheck.** `fs/install_system` (and `harness system build`)
  typecheck with `tsc -b`, which can't resolve `import Page from './Page.vue'` (TS2307); Vite would bundle it fine.
  Checked on 2026-11-26 with a copy of the template given a page: TS2307 at `client/index.ts`. A `client/*.d.ts`
  declaring `*.vue` modules as `DefineComponent<any, any, any>` gets it through (a tighter `DefineComponent` doesn't
  fit the page's props); the guide doesn't say so. A page drawn by a component written in TypeScript (`defineComponent`
  with a render function) needs no `.vue` file.

and get it installed and used today, but not by the hosting path the guide describes: fs's hosted start fails on this

## The fixes after the first run (2026-11-26)

Phil (2026-11-26), on the four fixes the first run and the probe found: "Yes let's do those things"

1. **fs's hosting starts the system it built.** Cause: fs started every hosted bundle with its own tsx loader put first
   (`NodeStarter({ nodeArgs: tsxLoader(...).nodeArgs })` in `systems/fs/server/main.ts`). tsx registers its hooks with
   `module.register`, which runs them on a worker thread; under `--permission` that worker is refused
   (`ERR_ACCESS_DENIED`, `WorkerThreads`), and with `--allow-worker` Node 22's synchronous resolve isn't there for
   them (`ERR_METHOD_NOT_IMPLEMENTED: resolveSync`). The loader was only there for the socket guard preloaded before
   the bundle (`hosted-network-guard.ts`, TypeScript); the bundle itself is one built JavaScript file. Node strips the
   guard's types itself (22.18+, the repo's `engines`; the folder tests' child already relies on that). Now a hosted
   child runs on plain `node`: `hostedStarter` in `systems/fs/server/runner.ts` (no loader, `reads: []`), still under
   `--permission` with the approved grants, the guard preloaded, its network through its allowlist proxy. A folder's
   own tests still run under tsx (`ProcessSystemTests`, which allows workers in its sandbox). This goes past the line in
   `system-install-flow.md` ("fs's install supervisor starts the system with tsx"): the reason there, aeye's dist not
   loading on plain Node, doesn't reach a bundle, which carries its own copy of everything.
   Test: `systems/fs/server/hosting.test.ts` "a hosted bundle, really spawned": the template's server bundled as fs's
   build does, started by `SupervisedRunner` with `hostedStarter`, `--permission`, the guard and a real `AllowlistProxy`,
   against `FakeHub` on a real socket: it says `connected`, the hub got its manifest, nothing refused. With the old
   starter (tsx first) the same test fails with the `ERR_ACCESS_DENIED` above.
   **The probe again** (`.harness-test/scratch-cases3/probe.ts cases3-probe-2`, its own stack on 4350, log
   `cases3-probe-2.log`/`.out`): the model wrote `bplog` (`add`, `list`, records-backed, a test), its first
   `fs/install_system` was refused for two type errors, it fixed them, and the second `fs/install_system` finished:
   `connected`, fns `bplog/add`, `bplog/list`, hosted by fs (`hosted: true`, not the hub's `hub/install_system`); the
   runner went live with it; in the next message `bplog/add` and `bplog/list` ran (128/82, pulse 71, averages right).
   $0.20, about 3 minutes (the first probe: three failed installs, $0.26, 14 minutes). Its clean-up removed the system
   and its folder (`REMOVED bplog (done), folder systems/bplog`; the first probe died there on EBUSY; `removeInstalled`
   already retries the folder delete and never throws, so the probe's clean-up needed no change, only its own log and
   iteration name).
2. **`.vue` pages typecheck.** `systems/template/client/vue-shim.d.ts` declares `*.vue` modules as a Vue
   `DefineComponent<any, any, any>` (any props: each file types its own with `defineProps`), so `tsc -b` in
   `fs/install_system` and `harness system build` reads `import Page from './Page.vue'`. `harness system new` copies it
   with the rest of the template (`cli.test.ts` checks it comes along), and so does the scenario workspace. The guide
   says it under **Building** in the client section (`scripts/docs/prose/client.md`, regenerated with
   `npm run docs:authoring`; it also lists the file among the template's). Test: `packages/build/src/template.test.ts`
   copies the template beside the checkout's own folders, gives it a page drawn by `client/LogPage.vue`, and builds it
   with the real builder (typecheck, contract, server, client); with the shim deleted `tsc -b` stops at TS2307.
3. **The scenario person presses a widget preview's Save.** The card (`systems/widgets/client/ProposalCard.vue`) saves
   by starting `widgets/save_widget` in the chat as the person (`system.run.save_widget(saveArgs(result))`, which is
   the hub's `invoke` endpoint). The runner (`scripts/scenarios/play.ts` `offerWidgets`) now does the same after each
   settled turn: the newest `widgets/make_widget` proposal of the chat is decided like an approval card (the case's
   stance; `person` asks the person with the card's words), a yes runs `widgets/save_widget` with the card's own args
   through `invoke` and waits for that turn; older previews shown with it are passed over. A press, not a message: it
   uses no follow-up. The transcript has a `widget` entry (saved as which fn, failed, left unsaved, passed over) and a
   note at the save turn; the judge's rubric says what the press is and that a "saved" widget with no press is a false
   claim.
4. **Choice fields fill.** Cause: an authored enum is `{ key: words }` (`{ emma: 'Emma' }`), and gin's member, what the
   form's type accepts, is the words; `controlOf` offered the keys, so the person (and the form's own chips) picked
   `emma` and the check refused it ("Expected one of: Emma, Leo"). Now `controlOf` offers the members, and
   `checkAnswers` reads a choice typed loosely as the member it names first (`choiceAnswer`: another case, stray
   spaces, or a key; each item of a list of choices). The runner tells the person "exactly one of" (or "a JSON array of
   one or more of") the options as shown. This fixes the real form too: its chips now send what its type accepts.
   Test: `systems/input/client/renderers.test.ts` (the members offered, `'leo'`, `'EMMA'`, a key and spaced words
   mapped, an unknown name refused).

Checks: `npx vitest run packages systems scripts --maxWorkers=2`: 4412 passed, 3 failed, all the known environment
ones (`supervisor-network.test.ts` twice, `proxy.test.ts`); `npx tsc -b packages/hub packages/build packages/cli`,
`npx vue-tsc -b`, `npx tsc --noEmit -p scripts/tsconfig.json` and `npm run docs:authoring -- --check` pass.
