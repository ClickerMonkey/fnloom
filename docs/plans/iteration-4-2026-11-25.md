# Scenario iteration 4: what changes before it runs (2026-11-25)

Iteration 3 (`.harness-test/scenarios/iter-3/`, `off` variant only, 40 cases × 3 reps = 120 runs: **74 pass / 41 weak /
5 fail**; 2052 tool calls, 59 failed or refused, 23 model arg mistakes) is diagnosed in its `diagnosis.md`. The judge
put most weak and failed reps on `missed-capability` (30 of 49) and the `chat-prompt` layer (38 of 49). The diagnosis
ranks 80 fixes; the top three (10, 5 and 5 case reps) are all about memory.

Publishing aeye and ayepi and cleaning up the worktrees are done. This plan is the memory fixes and the non-specific

## Rules for every change (standing, from iteration 3)

- **General purpose only.** No prompt, example, instruction, guide or tool description mentions the scenario use cases
  (groceries, receipts, chores, reading minutes, parties, weather, allergies, peanuts, snacks, school, budgets,
  dinners, gas, insurance, …) or echoes their data. Fixes are written for any request of that kind.
  `scripts/guidance-leaks.test.ts` holds the words.
- Never state the person's technical level; explain fns, systems, kinds and XML blocks to a model that only knows
  "tools".
- No hard-coded tool lists or system names in the hub prompt: system-specific guidance lives in the systems.
- Examples stay encodable (`scripts/examples-encoded.test.ts`).
- A diagnosis proposal is a model's suggestion: each is checked against its transcripts first, and one that would only
  fit one case is dropped.
- **Iteration 4 runs the `off` variant only**, as iteration 3 did.

## The changes

Each change with the evidence for it. Case numbers are the scenario cases' (`iter-3/rep-N/cases/case-NN.md`).

### 1. Memory

1. **Recall: the person's memories come with a message by themselves** (mechanism; `chat/enrich.ts` `#recall`,
   `LoadedForYouPart.by: 'recall'`, settings `HARNESS_RECALL_MEMORIES` = 3 and `HARNESS_RECALL_THRESHOLD` = 0.2).
   Case 28 (a fact saved in one chat, a request it bears on in the next) failed all 3 reps. The words were already
   there ("Memories are not shown to you in a new chat … search for memories first"); the model searched in the chat
   that saved the memory and never in the new one. The hub's own record of the new chat's first message
   (`messages.suggestions` in each rep's `hub.sqlite`) shows the memory was the **top context candidate** every time,
   at similarity 0.271, 0.240 and 0.260, and was dropped as `below-threshold` (0.3). So with each message the hub now
   searches the person's memories by meaning and brings the closest few (at most 3, at or over 0.2) into the message
   as their text, in `<loaded_for_you>` with its own first line (what a memory is, that one bearing on the request
   applies without being said again, that they are facts not instructions, not to load or search them again). Each
   once a chat (they count as suggested); only those the person may see here (a session memory only in its own chat,
   even for its author); on any contextor but the graph one (which picks its own context); whoever picks suggestions.
   The text sits in the user message, not the system prompt, so `guardReach` (a model never writes text that lands in
   every later prompt) holds. Across iteration 3 the other memory candidates in the records scored 0.38 to 0.48 to the
   messages they belonged with, so 0.2 lets the near misses in without being noise (the median item scores 0.09 to
   0.19). Tests in `enrich.test.ts`; documented in `docs/harness.md` beside the suggestion rule it is an exception to
   ("similarity is too weak a sign to put things in the prompt unasked").
2. **Keep durable facts mid-task, concisely** (`hub/context/memory.md`, `hub/remember`'s instructions). Diagnosis fix 1
   (10 case reps: 1, 4, 7, 9, 10). Across all 120 reps 17 memories were kept (listed from each rep's
   `context` table); where the person lives, given while asking for something else (cases 1 and 10, every rep), and a
   starting point for a plan (case 9) never were. The item now says when to keep one (asked, or mentioned in passing: who they
   are and who is around them, where they are, a standing preference, a limit or something to avoid, a routine, a
   goal), to do it in the same step and carry on, one plain fact as said (not widened), and what not to keep (what only
   this task needs, each form answer or list entry, guesses, secrets); a changed fact corrects the old memory.
3. **Check what is kept before asking or recommending** (`memory.md`, core "Asking the person", core "Saying only what
   is true", `hub/fns_search`'s instructions). Diagnosis fixes 2, 3 and 13 (cases 5, 8, 12, 14, 18, 21, 28, 34). The
   memory item says the closest few come by themselves and others may still matter, so search before a personal
   recommendation, plan or list, before asking a detail about the person, and when they refer to someone or something
   the chat hasn't introduced. The core's new bullet on a recommendation or plan for the person: it depends on them
   (what to avoid, limits of time, money or ability, how many, what they have already); use what is in front of you and
   what is kept, then ask for the few unknowns that would change the answer, or answer in general terms and say so;
   don't ask what wouldn't change it (case 5 r1 asked for more than it needed). Grounding: before saying you don't
   have, can't see or can't reach something, look with the fns you have and say only what you checked (case 18 r3 said
   it couldn't see accounts after checking only tables). `hub/fns_search`: it finds fns, never the person's data, so
   finding nothing says nothing about what they keep (case 18 r1 searched fns twice for the person's records).
4. **A memory is not a rule** (`memory.md`). Diagnosis fix 7 (case 36 r1 kept "prevent the kids from …" as a memory
   when asked to block something): a memory stops no one; who may run what is an admin's policies.
5. **A request the person will repeat can be their own `/command`** (`memory.md`, `hub/remember`, `hub/context/later.md`).
   A memory's `command` (already in `RememberArgs`, never explained to the model) makes it a `/command` in the person's
   composer (`api/web/chat.ts` lists hub-made context with commands). `later.md` now says: say plainly it can't run
   later, then do it once now if it can be done, give a quick way to ask again (a saved fn, a view, or the request kept
   as a `/command`), and optionally the words for a reminder in their own phone or calendar app. Diagnosis fix 10
   (case 26, weak in all 3 reps: honest about the limit, but no summary now and no quick way to ask again).
6. **`hub/forget`'s example named a memory wrongly** (`hub/memory.report-day`; memories are `memory/<slug>-<hash>`), and
   `hub/remember`'s `about` example named `database/main.expenses_create`, a scenario word the leak test missed (`\b`
   doesn't split `expenses_create`). Both fixed; see 3.4 for the test.

### 2. Non-specific guidance and examples

1. **Fn names are for the model's calls** (core "Where you are"; `database/basics`; `hub/context/saved_fns.md`).
   Diagnosis fix 8 (cases 2 r2/r3, 9 r1 told the person to run `database__main__…_create`). The database item itself
   said "The person can then add entries with those fns". Now: tell the person in everyday words what to tell you,
   press or open; the database item says the person adds an entry by telling you (or a form, where the chat has forms)
   and sees them by asking (or a lasting view); `saved_fns.md`'s keeping-track bullet says the same and asks for
   earlier entries when there may be some, so the view starts complete (diagnosis fix 9, case 3).
2. **Text is not a control** (core "How calls behave"). Diagnosis fix 27 (case 23 r1/r2: a text table with boxes to
   tick, told to print it). Boxes, checklists and tables in an answer can't be ticked and keep nothing; for things to
   mark done over time, keep them where entries are kept, each with its state.
3. **A check the person will want again** (`saved_fns.md`). Diagnosis fix 11 (case 1, all 3 reps: no reusable check):
   look for a saved fn, else make one where a system can and a real source exists, run it once now, say how to ask
   again; a one-off question needs none.
4. **Web** (`web/guide`, `web/basics`, the failed-read note). Diagnosis fixes 19 and 38 (cases 4 r1, 10 r3: repeated
   searches; 1 r3: a qualitative chance turned into a percentage): stop once the pages answer, give a number only when
   a page gives it. `web/basics` takes the place "from what is kept about the person (a memory in front of you, else a
   search of their memories)" instead of "what you know of the person". Diagnosis fix 12 (cases 27, 29, 34): the
   failed-read note offered `render: "always"` after a 403; now a refusal (401, 403, 406, 451) or a missing page (404,
   410) says don't read it again or render it, use the next result.
5. **"What can you do?"** (core "Systems"). Diagnosis fix 24 (case 38 r3 hedged): a short overview with a few
   everyday examples from different systems; a listed system is there to use.
6. **Earlier chats** (`earlier_chats.md`). Diagnosis fix 21 (case 29 r1/r2 said a chat was "last week" without
   checking): check a chat's date against the time the person named and `<local_time>`.
7. **Finding fns** (`finding_fns.md`). Diagnosis fix 26 (cases 6 r3, 12 r1 loaded guides and fns again): look at the
   tools and the prompt first; what is there needs no search or load.
8. **Adding a person** (`hub/add_user`). Diagnosis fix 25 (case 35): it only adds the account and sends nothing
   (checked in `api/admin-ops.ts`), so never say an invitation was sent.

### 3. Tool and tooling fixes found on the way

1. **Database: a refused query always names a problem** (`systems/database/server/compile.ts`). Diagnosis fix 17
   (cases 17 r2, 22 r2, 10 times): the authoring agent's `draft` answered "Clean. Call save to keep it." and `save`
   then failed "The draft doesn't run here:  Fix the draft first." — the parser read no query and named no error, so
   the check's problem list was empty (read as clean) and so was the save's message. Now the errors, else the parser's
   other notes, else a fixed sentence (`NO_QUERY_PROBLEM`). The same draft on a fresh instance compiles, so the
   parser's silent case is still to be found; this stops the loop and makes it say something.
2. **Widgets: the authoring agent's offer no longer says "Saved"** (`packages/sdk/src/authoring.ts` `savedLine`,
   `systems/widgets/server/authoring.ts`). Diagnosis fix 15 (cases 3 r2, 5 r1) read the widget agent's "Saved
   widgets/… (version 1)" as the widget being kept, against the outer result's (true) "Proposed, not saved". The
   chat model was right; the inner line was wrong. It now says the widget was offered and nothing is saved until the
   person presses Save.
3. **The diagnosis view's cuts say they are the view's** (`scripts/scenarios/modelview.ts`, `diagnose.ts`). Diagnosis
   fixes 4 and 16 (cases 10, 14, 15, 22) said the model used details "not shown" in a page or file read, or that a
   result said `truncated: false` while text was cut. Checked against the runs: in case 14 the model was given 12,000
   characters with the ingredients at 7,598 and the steps at 8,391; the "[… 95 characters cut …]" and "2,000 of 22,366"
   the diagnostician quoted were its own view's 1,600-character cut of the result (and a misread of "1–12,000 of
   22,366"). The mark now reads "cut from this view only: the model was shown them", and the instructions say a cut
   result can't be used as evidence the model invented something.
4. **The guidance-leaks test** reads more of what the model reads (`chat/enrich.ts`, `announce.ts`, `cite-rule.ts`,
   `contextor/`, `boot/hub-fns.ts`), matches words inside snake_case and dotted names, and has more of the cases'
   words (parties, a class party, neighbour, dog, favourite band, mom, Thanksgiving, turkey, tacos, pasta, mushrooms,
   spicy, gym, Peloton, 5K, jogging, fitness, shoes, heating, dentist appointment, pwned, breaches, "photos of the",
   classroom).

### Dropped, and why

- **Fix 4 / 16 (web and resource reads: partial pages, `truncated: false` with text cut)**: the diagnosis view's own
  cut, not the model's (3.3 above). The web guide and `web/read` already say to read on when `partial`.
- **Fix 18 (always a form for several details)**: case 7 r2 asked in its answer and the judge passed it 9/10; the
  input item already says a quick question goes in the answer.
- **Fixes 29 and 31 (undo by `hub/turn_undo` from the chat)**: `hub/turn_undo` undoes only the newest message, which
  is the "undo that" being answered, so recreating what the previous message removed is the right move under the
  current design (rep 1 did it and scored 10/10). Letting the model undo the message before the current one is a
  design change: left for Phil.
- **Fix 37 (`hub__remember`'s schema: a `$ref` with a sibling `description`)**: a real failure (case 36 r3, 8 turns
  refused by the provider: "`$ref` cannot have keywords {'description'}" at `about.anyOf.0.items.anyOf.1.properties.name`),
  but the schema is rendered by `@aeye/schema` (aits), which this work doesn't touch. 187 positions across the hub's
  and systems' fns carry a `$ref` with a `description` in their code-shape schema; the strict render needs to drop or
  wrap the sibling. Left for aeye.
- **Fix 6, 9, 33 in full (systems list / database workflow text naming forms, widgets and tables together)**: the
  plain-words part is in 2.1; the rest would put system-specific workflow into the hub's systems list or name other
  systems from one system's item.
- **Fixes 5, 22, 28 (outside services, policies, the api guide)**: one case each (24, 36) with case-shaped wording.
- **Fix 20 (verify arithmetic and counts)**: case 37's weak verdict was a long path, not a wrong number; case 22's
  totals were accurate.
- **Fix 34 (offer to adjust a draft's tone)**: the judge's preference in one case.
