## What it means (my reading; the owner can overrule)

### 1. Authoring fns behave like product's

- **The pattern:** for queries, inputs (gin types), and later APIs and code, the chat model calls one authoring fn
  (`get_query` / `edit_query`, `get_input`, and later `get_api`, `get_code`, …) and passes a full description of
  what it wants. It never generates the artifact itself.
- **Inside the fn:** a sub-agent, on `ctx.ai()` (aeye through the hub), does the work. Its tools force a fixed
  workflow (find existing → inspect types → draft → check → fix → save), and progressive disclosure shows it types,
  schemas, examples and docs a little at a time. The huge context these artifacts need stays inside the fn, so the
  main chat stays small.
- **Port, don't reinvent:** take product's tested logic from `C:\Users\pdiff\Documents\GitHub\product`: its query
  agent and `query_set`, its type agent, its gin expression authoring, its disclosure steps and their tests. Port it
  onto aeye as-is where possible, with its unit tests. Library pieces belong in `@aeye/query` and `@aeye/gin` (see
  `docs/research/database-vs-product.md`, recommendations 1–3: one type model via `tableToQueryType`, the typed
  authoring schema via `buildSchemas`/`buildQueryTool`, signature and arg-check helpers).
- **Shared helpers:** the forced-workflow agent is one reusable SDK helper (an "authoring agent": stages, tools per
  stage, disclosure, a check-and-fix loop, a save step). Query, input, and later API and code authoring all use it.
- **What the chat model gets back:** the saved fn's signature, what it does, the result or preview, and how to call
  it again. Never the whole working context.

### 2. Testing is native to a system

- **One SDK test kit** that system authors (and the chat, when it writes a system) use without setup:
  - **Fake hub:** a fake hub and context in one line, with every `ctx.*` faked and recorded.
  - **Fn calls:** call a fn with typed args and check its typed result, its progress and what it asked the hub for.
  - **Mock and real models:**
    - mocked LLM replies (scripted, or recorded and replayed) for fast unit tests
    - real LLM calls for a few marked tests, through the hub or a free model, skipped without keys
  - **Component previews:**
    - render a system's Vue components (renderers, visuals, inputs, editors) in isolation, in named states (empty,
      loading, error, typical data, long data, phone and desktop)
    - screenshot them so a model or a person can review them, as a gallery
  - **Kinds and contexts:** test a kind's derived fn props from a payload. Test a context folder: it is valid, its
    links resolve, and it loads its fns.
- **Native, not bolted on:**
  - `harness test` runs a system's tests from anywhere.
  - fs's `install_system` runs them before asking for approval and shows the result on the card.
  - The authoring context teaches the kit, and the chat writes tests with the systems it writes.

### 4. Generated fns from a table type (owner, 2026-11-11)

> There should be a tool that given a type from a database can create any number of autogenerated fns. Obviously create, update, updateWhere, remove, removeWhere, selectOne, selectPage, and then based on the columns/fields/fks there could be aggregate handy fns. So a fn should be able to given a type list out all possible handy fns we could create, and then another fn that can create/update them by name.

- **`database/table_fns_available(type)`** lists every fn that could be generated for a table type. Each entry has
  its name, what it does, its signature and whether it writes. Entries that already exist are marked, with their
  version. The list covers:
  - **CRUD:** `create`, `update` (by key), `updateWhere`, `remove` (by key), `removeWhere`, `selectOne` (by
    key or unique columns) and `selectPage` (filters, sort and paging from the query standard).
  - **Helpers derived from the columns:**
    - counts and group-by counts on enum and low-cardinality columns
    - sum, avg, min and max on number columns
    - date buckets (per day, week or month) on date columns
    - lookups by each unique column
    - for foreign keys, a parent with its children, children of a parent, and counts per parent
    - exists / find-or-create on unique keys
- **`database/table_fns_generate(type, names[])`** creates or updates the named fns as hub fns of the query kind,
  with real instructions and examples. It is idempotent by name, keeps version history, and regenerates when the
  table's schema hash changes.
  - **Writes:** fns that write go through approval as usual.
  - **Visibility:** generated fns get the instance's visibility. The admin can change each one.
- **Owner: "No model involved for those, but authoring generic queries - yes".** The generated table fns are plain
  code. Generic queries (`get_query` / `edit_query`) stay model-driven: the authoring agent of section 1.
- **One pattern for every generator:** it's the authoring pattern of section 1, made deterministic (no LLM needed) and
  library-backed: the generators live in `@aeye/query`, beside `tableToQueryType`. Product's auto-CRUD is the
  prior art; port its tested parts.
- **Relationships (owner, 2026-11-11):**

  > And make sure it understands relationships... So if a table is projects ( id, name, owner, value ) and owner is ( id, name ) then owner might have fns like project count or project avg value or project total value. A project might have project owner relative amount rank or something like that (a record comparing it to others in related). Actually here are some notes I've captured before. This is a separate idea for building a graph from a table, but it has similar concepts as can borrow for this:

  The notes are in `docs/plans/database-graph.md`, word for word. What build 7 takes from them for generated fns:
  - **Derived fields from relations, computed in SQL by `@aeye/query`:**
    - **hasMany:** count; sum, avg, min, max and median of number and date fields; order rank (asc/desc) per sortable
      column; and all of these again split per enum value (`projectStatusDoneAvgAmount`).
    - **belongsTo:** the parent's fields and its own derived fields (`ownerProjectAvgAmount`).
    - **Table-wide:** the same aggregates over the whole table (`avgAmount`).
    - **Depth:** repeated across relations up to a depth N (default 2).
  - **Normalized comparisons, so a record can be compared with others in the same relation:**
    - count or order / count, for rank and percentile
    - value / sum, for share
    - (value − min) / (max − min), for position
    - value / max

    Each is labelled with what it means (progress, portion or relative). For example, a project's rank by amount among
    its owner's projects, and its share of the owner's total.
  - **Compatibility:** every derived field records its table and column, so only compatible numerators and
    denominators are combined.
  - **Fns from all of this:**
    - **In `table_fns_available`:** derived fields are offered as fns. Owner gets `projectCount`,
      `projectAvgValue` and `projectTotalValue`. Project gets `ownerRelativeValueRank` and
      `shareOfOwnerTotal`.
    - **As `selectPage` columns:** derived fields can also be added there, and `selectPage` can sort and filter on
      them.
    - **Limits:** the list stays readable for a small model. It is grouped by relation, with the most useful entries
      first and a cap with "more".
  - **Tests:** the projects/owners example end to end (SQL generated and run on SQLite), enum splits, a depth-2
    relation, and an incompatible combination being refused.
- **Tests:**
  - the list for a sample schema with an enum, a number, a date, a unique column and a foreign key
  - generation is idempotent
  - a schema change updates the fns

### 5. Installed vs live, review, and enforcement (owner, 2026-11-11)

> Good idea on hub enforcement - anything else like that you can think of so admins installing can inspect all the fns and what they do so they can decide to make it live or not. Once you install it's connected and hub is aware , but live is when it gets saved and is enabled. Before it goes live the admin gets to go in and review everything and configure it further etc. also a system should be able to specify a custom configuration component since gin based one might not be enough

**Lifecycle:**
- **Installed:** the system is paired and connected, and the hub knows its contract. Nothing it offers is live: no fn
  is offered to any chat or callable by anyone else, no context is suggested, no resources are indexed, no providers
  are used. The admin can make test calls from the review page.
- **Review page:** shows everything the system declares and adds:
  - every fn, with its instructions, signature, examples, kind, fn facts (types read and written, mode, free or not,
    cost and time estimates) and declared effects
  - its context (folder graph), types, kinds, resources and roots, components, providers and commands
  - its capabilities (below) and its configuration
  - its test results and scan report (install_system)

  The admin configures it, turns individual items off, sets visibility, and makes test calls.
- **Live:** the admin presses "Go live". The reviewed contract (with its hash) is saved, and everything enabled
  becomes available.
- **Changes after going live:** a new contract version, or a runtime addition outside what was reviewed, goes to a
  pending review with a diff. Meanwhile the live version keeps working, and the new or changed items stay off until
  approved. Additions within what was declared and reviewed (for example `database/query` fns from a fn that declares
  it creates them) are allowed, and they are listed on the system page.

**Enforcement: the hub checks what a system declared.** Each of these is declared in the contract, shown on the review
page and enforced over the link, with tests:
- **Effects** (above): undeclared registry changes are refused.
- **Mode:**
  - a fn declared `read` cannot call write or delete hub fns, propose writes, or write files through fs
  - `write` cannot delete
- **Types:** the types a fn declares it reads or writes are the only ones it can query or change through the hub.
- **Hub capabilities:** the hub calls the system may make, for example llm/ai, embed, resources, secrets, approvals,
  connections, other systems' fns or search. Calls outside the declared set are refused.
- **Models and spend:** the model roles or models it may use, and a per-run and per-day budget cap. Calls beyond them
  are refused.
- **Secrets:** it can read only the secrets it declared, by name.
- **Calling other fns:** it can call only the fns or systems it declared it calls.
- **Network and files** (for systems that fs installs and supervises):
  - **Network:** the hosts it may reach, enforced by the supervisor (Node's permission model plus an allowlist proxy).
  - **Files:** the paths it may read and write, enforced by Node permissions.
- **Visibility:** a system never gets data about a person who can't see it.
- **Audit:** every refusal is logged and shown on the system page. A system that keeps going past refusals can be
  paused automatically.

**Custom configuration:**
- A system can provide its own Vue configuration component (a client component in its contract). It is used instead
  of, or alongside, the gin form.
- The component gets the current config, its gin type, a validate callback (the hub still validates with the gin type
  before saving) and the system's client for live checks, such as testing a connection.
- It renders in the review page, on the system page and on the pairing page.

### 6. System graph and global graph (owner, 2026-11-11)

> Oh yeah and also a graph of the context and fns and anything else in a system to visualize it and things they reference that are not in that system are grayed out a bit. So a person can see what's in the system visually and how everything is connected and they can hover over the nodes or edges to understand what is everything and how it all relates. Also add a global view of sorts of the same sort of graph and we have filters to filter out certain nodes/edges

- **Nodes:** everything a system declares or adds: fns (by kind), context entries, types, kinds, resources and roots,
  components and registry contributions, commands, examples (collapsed into their fn), providers.
- **Edges:** the relations already recorded in the hub:
  - a context brings or names a fn
  - a context loads or offers next another context
  - a fn reads or writes a type
  - a fn calls or depends on a fn
  - a fn's kind
  - a fn's effects (it creates fns of a kind, adds context, …)
  - a type refers to a type
  - a component renders a type or visual
  - something belongs to a system or instance
- **The system graph** is a tab on the system page and on the review page. The system's own nodes are drawn fully;
  nodes it references in other systems or the hub are greyed. Clicking a greyed node opens it in its own system.
- **Hover:**
  - **A node:** its name, kind, a one-line description and its key facts: mode, effects, the types it reads and writes,
    visibility, on/off, and live or pending review.
  - **An edge:** what the relation means, in plain words, e.g. "fs.authoring.kinds brings fs/write".

  Clicking opens the item's detail, and fns open in the fn modal.
- **The global graph** is a page with all systems at once, with filters:
  - by system, node kind, edge kind, fn kind, mode and effects, visibility, live or pending, and on or off
  - search to focus on a node and its neighbourhood, N hops out
  - collapse a system into one node
- **The layout stays readable at scale:** clusters per system, progressive expansion, and "+N more" nodes. Light and
  dark, and it works on a phone with pan and zoom, tap for details.
- **One shared hub endpoint** returns the graph (nodes and edges, with filters, paged by neighbourhood), and the same
  query is a hub fn the chat can call, e.g. "how does fs's authoring context connect to the database fns?". Use a
  graph library suited to Vue (e.g. Cytoscape.js, or Vue Flow) rather than drawing by hand.
- **Tests:**
  - the endpoint's nodes and edges for a sample system
  - filters
  - greyed external references
  - one browser check of the rendered graph, since layout and hover can only be checked by rendering
