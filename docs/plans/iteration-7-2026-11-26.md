## 2. File types from their bytes; a bad picture never poisons a chat

**Evidence.** Case 50, all three reps: `Pictures/IMG_2890.JPG` is a real JPEG (`FF D8 FF E0 … JFIF`). hub/image_read
said `… IMG_2890.JPG is text/plain; charset=utf-8, not an image`; hub/resource_read gave `"form":"raw","text":""`;
hub/resource_send sent `{"type":"image","chars":38}`, and OpenAI answered `400 Invalid image data-url`. Every later
message failed the same way (`agent.failed … 400 Invalid image data-url`, rep 1's stack log), and the person gave up.

**Root cause** (not the extension's case: every lookup already lower-cased it). The fs system never sent a file's
bytes. Asked for `bytes`, `text` and `links`, `FsResources.read` always answered with its own text of the file (the
`@aeye/resources` parse), which for a picture (and a scanned pdf) is the empty string, and its stat carried no `mime`.
The hub kept that as the raw content: `forms.#fetch` stored the empty text as `text/plain; charset=utf-8` (every photo
in rep 1's `resources` table has `"served":"text"` and raw hash `e3b0c442…`, the hash of nothing). Then
`FormMessageContent` made an image part of it: `data:text/plain; charset=utf-8;base64,` (38 characters), and since a
shown resource is a reference expanded again before every call, the bad part went out on every turn after.

**Fixed.**

- `@harness/core` `media-types.ts`: `sniffMime` (magic numbers: png, jpeg, gif, webp, bmp, tiff, heic/avif, pdf, zip and
  office files, mp3, wav, ogg, flac, m4a/mp4/mov, webm/mkv), `mimeOfName` (extension, any case), `detectMime` (bytes
  first, name second, and a name that says text or picture never wins over bytes that say otherwise), and
  `imagePartProblem` (what may go to a provider as a picture: an http(s) URL, or a base64 data URL of png/jpeg/gif/webp
  whose bytes really are that picture).
- fs (`systems/fs/server/resources.ts`): a file's stat has its `mime` from its first 4 KB, then its name, and a picture,
  pdf, recording or office file gets that format whatever its name says. Such a file is read **as its bytes** (up to
  the new `FS_RESOURCE_BYTES_MAX`, 25 MB), never as the system's own text; text named like a picture is read as text.
- SDK: a provider may hand over the bytes themselves (`ProvidedRead`, `ProvidedBytes`); the runtime holds them for the
  hub to fetch and sends their ref, as it already did for long text. The MCP resource bridge takes either.
- Hub: `forms.#fetch` stores bytes as what they sniff as, then the system's mime, then the name's; a kept snapshot is
  fetched again when the system's mime for it changed (so the bad snapshots kept before this are replaced). An upload
  is stored as what its bytes are (`library.#keepAt`).
- **The guard.** `FormMessageContent` sends an image part only when `imagePartProblem` passes, else a one-line note
  (`… can't be shown to you as a picture: <why>. Read what it holds with hub/resource_read …`). And at request time,
  like `closeOpenCalls`, `ConversationMedia.expand` ends with `pictureParts`: every image part in the conversation
  that isn't a real picture of a kind providers take becomes a short text note, for the request only (the kept
  conversation is never rewritten). The agent applies it on the media fallback path too.

**Tests.** `packages/core/src/media-types.test.ts`; `systems/fs/server/resources.test.ts` (a `.JPG`, a JPEG named
`.txt`, a pdf and text named `.jpg`: stat and read); `packages/sdk/src/server/resources.test.ts` (bytes handed over go
by ref and are served in chunks); `packages/hub/src/resources/content.test.ts` (a picture told by its bytes whatever
the stat says; a picture a system sent as empty text becomes the note); `packages/hub/src/chat/shown.test.ts` (the
case-50 part in a kept message becomes a note and the next message is untouched; a shown fake picture likewise).

## 3. PDF pages

**Evidence.** Cases 57 "Name my scans" (weak all reps) and 49 r1: the fs-served scans read as `"form":"raw","text":""`
with no offers; `hub/resource_send` with section `Page 1` returned a 143-character text part (the page's empty text
under a heading); `resource_read` with form `ocr` or `pages` was refused ("has no ocr form; it has no form that reads
as text yet. Look at it with hub/resource_send instead", which it had just done). The model then probed the machine
with `fs/bash` for pdftoppm, tesseract and Python packages, the person declined, and the scans were renamed by date.
Case 52's attached text pdf (the neighborhood rules) read fine as `pages`: its weak verdicts are item 5's.

**Root cause.** The same as item 2 for files the fs serves: a pdf came as the system's own (empty, for a scan) text,
so the hub never converted it into pages. And even with pages, a page with no text had no picture to give.

**Fixed.**

- With item 2, an fs pdf comes as its bytes and the hub converts it to its `pages` form: a text pdf reads as its text
  page by page, a page section as that page's text.
- `packages/hub/src/resources/pdf-pages.ts` reads each page's picture straight out of the file, no renderer needed (a
  scan is one picture per page): a JPEG as it is; a Flate bitmap (grey or RGB, 1–8 bits, PNG row filters undone, a
  soft mask laid over white) as a PNG; plain objects and object streams; the page tree in order with inherited
  resources; pictures inside form objects. It never throws; what it can't read (JPEG 2000, JBIG2, fax, palettes, CMYK)
  has no picture. On the four real scans of the fixture home it gives each page in ~40 ms.
- `FormMessageContent`: a pdf (or one page) with no text goes to a model that sees as a line saying its pages are
  pictures, then the page pictures (the first 4 of a whole pdf, `PICTURE_PAGES`; one for a page section), with how to
  see another page; to a model that can't see, a note on asking hub/image_read about a page; a page with neither text
  nor a readable picture says so plainly ("tell the person, and don't guess"), so nothing pretends to have been shown.
- `hub/image_read` takes a pdf whose pages are pictures: `page` (from 1) asks about one page; without it, the first 4
  pages are asked in turn. The args gained `page`; the fn's instructions and a new example say so.
- `hub/resource_read` of a pdf with no text at all adds a `note`: its pages are pictures, there is nothing to read
  here, see a page with hub/resource_send (section "Page 1") or ask hub/image_read; don't guess.
- Guidance: `hub/resources` (a file with no text reads as empty, which is not an empty document; look at it; leave out
  `form` unless a result listed it; say which files couldn't be read and never name them by a guess), `hub/images` (a
  scanned pdf's page is asked the same way), `hub/resource_send`'s instructions, and the fs guide (fs/read is text
  only; pdfs and pictures go through the hub fns by their uri).

OCR: the `ocr` form is a model-made form of pictures (the `ocr` role). For a scan, the vision model through
hub/image_read is the way to the words; the read's note and the refusal no longer leave it unclear.

**Tests.** `packages/hub/src/resources/pdf-pages.test.ts` (JPEG and bitmap pages in order, a text page with none, a
soft mask over white, junk and a cut file never throw, the PNG writer); `content.test.ts` (a scan sent whole and by
page to a model that sees, the no-picture page note, the blind model's note; a text pdf whole and by page; the read's
note); `fns.test.ts` (hub/image_read on page 2, on every page, and past the last page). The tests make real pdfs with
`madePdf` (`resources/testing.ts`): a catalog, page tree, image or text pages and a correct xref table.

## 4. Runner isolation

**Evidence.** Rep 3: case 47 ("Who uses this?", read-only) turned off ten accounts with hub/update_user, among them
case 49's person, created moments before (case 49: "the runner failed: user not found"); case 48 turned Leo off. The
rep's `actors` table still shows case-41 … case-49's people disabled. Cases share their rep's hub, three at a time.

**Fixed** (`scripts/scenarios/household.ts`, documented in `run.ts`'s header):

- **The household is put back before and after every case.** At rep start (after the variant) the rep snapshots the
  sign-in policy and every rule (policies, budgets, priorities, model categories) and keeps every account it makes:
  the kids' logins, each case's own person (admin) and each member made for a case. `Rep.restore` turns those accounts
  back on with their roles, removes every rule added since, and puts the sign-in policy back. A case's own person is
  always put back; a member made for a case still playing is left to that case. A kid's login that is gone is made
  again. Accounts nobody made for the rep are left alone.
- **Household cases play alone.** `Case.household` marks the cases that change accounts, rules or budgets (35, 36, 46,
  48, 71, 72) or read them where an agent changed them unasked (47). `CaseGate` lets ordinary cases play together and a
  household case only alone; a waiting household case goes before ordinary cases that come after it.
- **A person who can't sign in is made again.** `Rep.person` turns the account back on and tries again, and failing
  that makes the case a new account under a new address rather than failing the case.

**Tests.** `scripts/scenarios/household.test.ts`: what one agent changed (accounts off, a role, a policy and a budget,
the sign-in policy) is all put back and an untracked account left; a playing case's member is left to it but its
person isn't; a gone account is reported; the gate's order.
