## Rules for every change

- **General purpose only.** No prompt, example, instruction, guide or tool description mentions the scenario use cases
  (groceries, receipts, chores, reading minutes, parties, weather, allergies, …) or echoes their data. Fixes are
  written for any request of that kind. Text already written that way is removed.
- **Iteration 3 runs the `off` variant only** (the baseline); `on` and `load` come back in later iterations.

## The work

1. **One spelling in every field.** Every arg and result field that names a fn, a table, a type or a widget source
   accepts and shows the same model names the model sees elsewhere (the `names` and `types.reads/writes` filters of
   `fns_search`, database `table` values, widget sources…). Database: `writes` says whether rows can be written, and its
   examples stop mixing table names with tool names.
2. **Say when a result is partial.** A result that was truncated, a read that failed, or a form that isn't available
   says so in what the model reads, with what is available instead (a PDF's pages, a sheet's table). Search finds the
   exact guide or item asked for by name even when a decision filter is on.
3. **Images for models without vision.** When the chat's model can't see images, an image in the conversation is
   replaced by an XML block describing it with an id, and an image-read fn takes that id and a question and sends both
   to a vision model an admin configures, returning its answer. The test hubs configure that model.
4. **Model mistakes are not errors.** Invalid tool args (the model's mistake, which it recovers from) are kept apart from
   tool failures everywhere: records, metrics, the UI (a calm status such as "thinking harder", a warning at most, saying
   it has no bearing on the result, never an error) and the scenario judge, checks and diagnosis (recovered arg mistakes
   are not failures; not delivering a good result is).
5. **Guidance audit.** Remove use-case-specific text added so far; memory and keeping-track guidance stays general.
6. **Diagnosis check.** A Haiku review of a sample of iteration 2's diagnoses, especially the steps filed as model errors.
