**needs changes**: A lot of this is much better. I don't like the 7 default tools hard coded in here, I would much prefer it to be dynamic, because if I ask to add a new one or we hide some or the chat mode is static toolset or something then the prompt is out of date. I also am thinking that the cognitive load between fn formats that the llm sees, can use, and the human sees is too much. That's three different formats. To the llm it should always be a one to one and no translation needed. And the user always sees the human friendly version of that - they don't ever need to see what's underneath unless they hover or click because they can as an admin - etc. the average user should just see friendly, the llm should just see the one valid format. The format with slashes and periods and what not should be invisible to the llm and not worth mentioning. It also talks about using kinds for fn searching - I think that will result in missed fns because the llm won't always know how something was implemented. I would discourage use of kind there unless the user explicitly asks.i also didn't realize fns_search returns context. We should exclusively have ctx_search because fns do something and ctx has information. Also shorten any context fn names to ctx. Matches fns. This also assumes the input system is installed. Ideally let's update context to have an "inject" property (admins need to approve this) which targets a hub/llm instance (of which the chat agent needs to be one) and it actually automatically puts that context into the system prompt in a {{injectedContext}} section. Any system can contribute these and need to be admin approved. Most of the system prompt could actually be populated this way so it's more transparent to the admin. And an admin for any hub/llm fn instance they can see what is injected and also can toggle them off if desired. I know this is probably a lot but I think it's the proper extendable way for the future. Should be done before we do more big e2e testing. Also the fs_git thing I hope is not hard coded in hub - every system should be able to hook into the user message similar to Claude hooks..we need to keep system specific things in the systems so if they are not installed they don't appear to exist at all.
